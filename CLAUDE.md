# CLAUDE.md

Guidance for Claude Code when working in this repository. MikanMediaPipe is a standalone Windows tool for GPU hand and upper-body tracking from one or more webcams, streaming a parametric hand model over OSC to client applications (game engines, VMC receivers). Two name traps up front: it does not use the MediaPipe framework (it runs MediaPipe-derived and RTMPose models through ONNX Runtime with the DirectML execution provider), and it does not talk to MikanXR at runtime (some source was copied from that project, see NOTICE.md; the only runtime output is OSC over UDP).

## Working agreements

### Verification

- Verification is objective: run the SelfTest commands rather than assuming behavior. `MikanMediaPipe.exe --list-tests` enumerates them; each logs to `<flag>.log` next to the exe and exits nonzero on failure.
- Read the log, not just the exit status. Shell pipelines can mask a tool's exit code, and a replay tool that failed to load its input looks identical to a clean pass from the exit code alone.
- A change to fusion or any replayed stage is checked against recordings with `--replay-verify`. Checksum divergence on recordings made before the change is the diff of the change, not corruption; say so explicitly when reporting results.

### Determinism

- The replayed stages (`LandmarkTo3D`, `HandFusion` with its estimator, `BodyPoseSolver`) are deterministic by construction: no wall clock, no randomness, fixed iteration schedules. Anything added to them must preserve that, or record/replay silently stops being an instrument.
- Recording checksums are taken after fusion and before the IMU overlay and body solve, and they only verify against the binary that recorded them.

### Wire protocol

- The OSC schema is a contract with shipping consumers. Changing an address, type tag, or field meaning means updating the `OscStreamer.h` bundle-layout comment, the README tables, the self tests that decode the encoded bytes, and flagging the consumer change (see wire-protocol.md).

### Measured over assumed

- Model confidence outputs (MediaPipe presence, RTMPose scores) are never quality signals; they answer "is something here", not "is this estimate good". Judge quality with measured reprojection residuals, jitter stability, and replay A/Bs against recordings. This is cross-cutting lesson 1 in LEARNINGS.md and it is easy to undo accidentally.
- When optimizing or fixing a bug, stop before changing code and enumerate the plausible causes and courses of action, then weigh expected effect against effort. Prefer a replay A/B on a recording over reasoning from live impressions.

### Build gotchas

- CMake collects sources with `file(GLOB)`: a new `.cpp` needs a CMake re-run before it links, and a new `src/` directory needs a CMake edit (glob, sources, source_group, include dir).
- The exe must run with its working directory at the exe directory; model paths are relative and fail silently otherwise.
- `InitialSetup_x64.bat` deletes and re-downloads `deps/` wholesale (about 1.3 GB). Never store anything in `deps/`.

### Claude tooling gotchas

- Never compose C++ string or character content through bash or python heredocs: backslash escapes arrive mangled (a `\n` becomes a real newline inside the literal). Use the Write and Edit tools for source content.
- Edit-tool matches can fail on these CRLF files when the old string spans lines with leading tab indentation. Match a short unindented fragment instead.
- Check whether a directory predates the session before deleting it to clean up scratch files.

## Writing conventions (docs, comments, commit-adjacent text)

- Doc weight is proportional to significance: trivial changes get no doc at all (git is their record). A must-know convention gets a sentence, design weight gets a paragraph.
- Reference docs state current facts as plain fact. Verification history and adoption dates stay out; measured experiment verdicts live in LEARNINGS.md.
- Code carries no doc citations: source and build-file comments never point at a doc file. A comment states what the code needs in place. Docs cross-linking docs is fine. Code citing docs is not.
- Docs are public: stay neutral toward evaluated third-party projects, framing rejections as fit-with-goals rather than judgment.
- Plain text only: no em dashes, no icons or emoji, sparing use of semicolons. Prefer short sentences over semicolon chains.
- In reference docs, an inline enumeration of three or more concrete parallel items (commands, targets, type names) becomes a nested bullet list under the sentence that introduces it, one short item per line, no terminal period on bare items. Conceptual lists woven into an argument stay prose.
- Paths and path-like placeholders in markdown are always backticked (`docs/reference/build.md`, `models/<name>.onnx`): backticks read as code, and a bare placeholder in angle brackets otherwise parses as an open HTML tag and vanishes from rendered markdown.
- Markdown paragraphs and list items stay on one line (soft wrap only). Plan and multi-part progress items are "[ ]"/"[x]" checkboxes. Checking one off adds no inline rationale.
- A bulleted list whose items run two or more sentences is a loose list: one blank line between each pair of sibling items. Short single-sentence inventories stay tight. plan.md is exempt: its checkbox lists stay tight regardless of item length.
- Nested list items indent with tabs, one tab per nesting level, never spaces.
